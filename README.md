# 근태 모니터링 데모

가상 직원 50명의 8주치 출퇴근 기록에서 **주 52시간 초과 위험자**와 **지각·결근 패턴**을 찾아내고,
**팀장에게 보낼 주간 근태 요약 리포트**를 자동으로 작성하는 도구입니다.

- 모든 직원 이름과 기록은 무작위로 만든 **가상 데이터**입니다.
- Python 표준 라이브러리만 사용합니다. 설치할 것이 없습니다 (Python 3.11 이상).

## 어떤 HR 업무를 얼마나 줄이는가

대상 업무: **주간 근태 점검과 팀장 보고** (직원 50명, 5개 팀, 주 1회)

| 단계 | 엑셀 수작업 (가정) | 이 도구 |
|---|---|---|
| 근태 기록 내려받아 정리 | 10분 | CSV를 `data/` 폴더에 넣기 1분 (가정) |
| 직원별 주간 실근로 합산, 52시간 초과·근접자 확인 | 30분 | 자동 |
| 지각·결근 집계, 최근 4주 반복 패턴 확인 | 40분 | 자동 |
| 팀장 5명에게 보낼 요약 작성 | 50분 (팀당 10분) | 자동 |
| 인사팀용 전사 요약 작성 | 20분 | 자동 |
| 리포트 검토 후 발송 | - | 15분 (가정, 리포트 6개 × 2~3분) |
| **합계** | **약 150분** | **약 16분** (실행 자체는 0.1초 미만) |

**숫자의 근거**

- 수작업 150분과 검토 15분은 실제 회사에서 측정한 값이 아니라 **단계별로 추정한 가정치**입니다.
  회사의 근태 시스템과 담당자 숙련도에 따라 달라집니다.
- 실측한 값은 도구의 실행 시간뿐입니다. 이 PC에서 `python main.py` 전체 실행이 **0.04초**였습니다.
- 시간보다 중요한 차이는 **시점**입니다. 수작업은 주가 끝난 뒤 집계하지만, 이 도구는 수요일에 실행해
  "이 추세면 금요일에 52시간을 넘는다"는 사전 경고를 낼 수 있습니다. 데모 데이터의 마지막 주에서는
  실제 초과자 4명 중 3명을 수요일 시점에 미리 짚었습니다. 나머지 1명은 목·금요일 근무가 수요일까지의
  하루 평균보다 길어져 초과한 경우라, 수요일 시점 추세(예상 50.5시간)로는 잡히지 않았습니다.

## 실행 방법

```bash
python main.py
```

```bash
python main.py --as-of 2026-11-11
```

```bash
python -m unittest discover tests
```

- 첫 번째: 데이터 생성 → 탐지 → 주간 결산 리포트 작성
- 두 번째: 수요일 기준 주중 점검 리포트 (사전 경고)
- 세 번째: 단위 테스트 16개 (탐지 규칙 7개, MCP 서비스 권한·로그 9개)
- 실제 근태 CSV를 분석하려면 `data/employees.csv`, `data/attendance.csv`를 같은 형식으로 바꿔 넣고
  `python main.py --keep-data`로 실행합니다.

## 데이터

- 직원 50명, 5개 팀(게임QA, 모바일QA, 고객상담, 게임운영, 경영지원), 팀당 10명
- 기간: 2026-09-21 ~ 2026-11-13, 8주. 공휴일 4일을 빼면 근무일은 36일이고, 토요일 근무를 포함해 1,821행입니다.
- 컬럼: 날짜, 사번, 이름, 팀, 상태(출근/연차/반차/결근), 출근 시각, 퇴근 시각, 휴게시간(분)
- **지각은 CSV에 적혀 있지 않습니다.** 출근 시각과 출근 기준 시각을 비교해 탐지 단계에서 계산합니다.
  그래서 기준 시각을 바꾸면 지각 판정도 함께 바뀝니다.
- 50명 중 22명에게 탐지 대상 패턴 7종을 일부러 심었고, 누구에게 무엇을 심었는지 `data/ground_truth.csv`에 남깁니다.

## 출근 기준 시각 설정

`config.toml`에서 바꿉니다. 우선순위는 **개인 > 팀 > 기본값**입니다.

```toml
[work]
default_start = "09:00"      # 기본값

[[teams]]
name = "고객상담"
start = "09:00"              # 팀 전체 기준

[employee_start]             # 개인별 기준 (시차 출근)
E022 = "07:00"               # 조기조
E028 = "11:00"               # 늦은조
```

데모에서는 고객상담팀 3명이 07:00, 3명이 11:00 기준입니다. 예를 들어 07:00 기준인 직원이 07:20에
출근하면 지각으로 잡히고, 11:00 기준인 직원이 10:50에 출근하면 지각이 아닙니다.

## 탐지 기준

기준값은 모두 `config.toml`의 `[thresholds]`에서 바꿀 수 있습니다.

**주 52시간** (실근로 = 퇴근 - 출근 - 휴게, 월~일 합산)

| 등급 | 기준 |
|---|---|
| 초과 | 52시간 초과 |
| 위험 | 48시간 초과 ~ 52시간 이하 |
| 주의 | 44시간 초과 ~ 48시간 이하 |
| 사전 경고 | 기준일까지 누적 + (하루 평균 × 남은 근무일)이 52시간 초과 |

**패턴** (8주 전체 또는 최근 4주 기준)

| 패턴 | 기준 |
|---|---|
| 장시간 근로 반복 | 48시간을 넘은 주가 3주 이상 |
| 특정 주 근로시간 급증 | 52시간을 넘은 주가 있으나 위 '반복'에는 해당하지 않음 |
| 반복 지각 | 최근 4주간 지각 3회 이상 |
| 지각 증가 추세 | 최근 4주 지각이 3회 이상이면서 직전 4주의 2배 이상 |
| 특정 요일 편중 | 지각·무단결근이 5건 이상이고 그중 60% 이상이 한 요일 |
| 무단결근 반복 | 연차·반차가 아닌 결근이 2회 이상 |
| 휴일 전후 결근 | 공휴일 바로 앞·뒤 근무일의 결근이 2회 이상 |

처음 설계와 달라진 점: 요일 편중 기준을 "절반 이상"에서 **"5건 이상 중 60% 이상"**으로 올렸습니다.
지각이 서너 건뿐일 때는 우연히 같은 요일에 겹치는 경우가 많아 오탐이 늘기 때문입니다.

## 정답지 대비 탐지 정확도

`python main.py`를 실행하면 `output/accuracy.md`에 자동으로 기록됩니다. 아래는 시드 42 기준입니다.

- 심은 패턴 **22건 중 20건 탐지 (91%)**
- 탐지된 직원 21명은 모두 패턴을 심은 직원이었습니다. 정상 직원 28명 중 잘못 탐지된 사람은 없습니다.
- 전체 탐지 28건 = 심은 패턴 20건 + 함께 나타나는 것이 당연한 부수 패턴 6건 + 심지 않은 패턴 2건
  (부수 패턴 예: 월요일마다 지각하는 직원은 '반복 지각'에도 함께 걸림)

| 패턴 | 심은 수 | 찾은 수 |
|---|---|---|
| 장시간 근로 반복 | 4 | 4 |
| 특정 주 근로시간 급증 | 4 | 4 |
| 반복 지각 | 4 | 3 |
| 특정 요일 편중 | 3 | 2 |
| 지각 증가 추세 | 2 | 2 |
| 무단결근 반복 | 3 | 3 |
| 휴일 전후 결근 | 2 | 2 |

**놓친 2건**

- 월요일 편중으로 심은 직원 1명: 8주간 실제 지각이 3건뿐이라 최소 5건 기준에 못 미쳤습니다.
- 반복 지각으로 심은 직원 1명: 최근 4주 지각이 2회라 기준 3회에 못 미쳤습니다.

둘 다 지각을 확률로 생성하다 보니 실제 기록에는 패턴이 약하게 나타난 경우입니다.
규칙을 더 느슨하게 하면 잡히지만 그만큼 오탐이 늘어나므로 기준을 그대로 두었습니다.

**심지 않았는데 탐지된 2건**: 둘 다 다른 패턴을 심은 직원에게서 나온 추가 탐지입니다
(지각이 우연히 화요일에 3/5건 몰린 경우, 월요일 편중 직원의 지각이 최근 4주에 몰린 경우).

**시드를 바꿔도 비슷한가** (`python evaluate_seeds.py`, 시드 1~200)

- 찾은 패턴: 평균 21.6건 / 22건, 최소 20건, 최대 22건
- 심지 않았는데 탐지된 패턴: 평균 2.6건, 최대 12건 (200개 시드 합계 515건)

**심지 않았는데 탐지된 515건은 실제 패턴인가, 규칙이 잘못 짚은 것인가**

두 가지로 나눴습니다.

- **(가) 기록상 사실**: "4주간 지각 3회"처럼 횟수·시간을 그대로 말하는 규칙이 울린 경우입니다.
  원본 기록을 `detect.py`와 별도 코드로 다시 세어, 그 횟수·시간이 실제로 있는지 확인했습니다.
  정답지에 없었을 뿐 규칙은 맞게 짚은 것입니다.
- **(나) 우연을 경향으로 읽음**: "증가 추세", "요일 편중", "휴일 전후"처럼 경향을 해석하는 규칙이 울린 경우입니다.
  생성기에서 시간·요일·휴일에 따라 확률이 달라지는 직원은 해당 패턴을 심은 직원뿐이므로,
  그 외 직원에게 울린 것은 무작위로 생긴 쏠림을 경향으로 잘못 읽은 것입니다.

| 분류 | 패턴 | 건수 | 정상 직원 | 다른 패턴을 심은 직원 |
|---|---|---|---|---|
| (가) 기록상 사실 | 반복 지각 | 54 | 39 | 15 |
| (가) 기록상 사실 | 무단결근 반복 | 18 | 18 | 0 |
| (가) 기록상 사실 | 근로시간 (급증 3, 반복 3) | 6 | 0 | 6 |
| **(가) 소계** | | **78 (15%)** | 57 | 21 |
| (나) 잘못 짚음 | 지각 증가 추세 | 374 | 37 | 337 |
| (나) 잘못 짚음 | 휴일 전후 결근 | 33 | 0 | 33 |
| (나) 잘못 짚음 | 특정 요일 편중 | 30 | 1 | 29 |
| **(나) 소계** | | **437 (85%)** | 38 | 399 |

- (가) 78건은 원본 기록 재집계에서 **78건 모두 일치**했습니다. 규칙이 없는 사실을 만들어 낸 경우는 없습니다.
- 잘못 짚은 437건 중 **374건(86%)이 '지각 증가 추세' 규칙 하나**에서 나왔습니다. 원인은 두 가지입니다.
  - 지각이 원래 잦은 직원(반복 지각형, 월요일 편중형)은 확률이 일정해도 4주 단위로 보면 2회 → 4회처럼 출렁입니다.
  - 직전 4주에는 공휴일이 4일 있어 근무일이 16일, 최근 4주는 20일인데 **횟수**로 비교했습니다.
- 시드당으로 보면 잘못 짚은 것이 평균 2.2건, 기록상 사실이 평균 0.4건입니다.
- 잘못 짚은 437건 중 399건은 이미 다른 패턴으로 확인 대상에 오른 직원에게 붙은 추가 표시입니다.
  정상 직원에게 잘못된 경향 표시가 붙은 것은 38건(시드당 0.2건)입니다.

**개선안 실험** (규칙에는 아직 반영하지 않음): '지각 증가 추세'를 횟수 대신 근무일당 비율로 비교하면,
심지 않은 탐지가 374건 → 209건으로 줄고 심은 패턴 탐지는 391건 → 388건(400건 중)으로 거의 유지됩니다.
절반 가까이 줄지만 완전히 없어지지는 않습니다. 4주라는 표본이 작아서 생기는 출렁임이 남기 때문입니다.

**이 숫자의 한계**: 이 정확도는 "내가 심은 패턴을 내가 만든 규칙이 찾는가"를 확인한 것입니다.
규칙이 의도대로 동작한다는 검증이지, 실제 회사 데이터에서의 성능을 뜻하지 않습니다.

## 리포트

- 팀장용: 한 줄 요약 → 근로시간 표 → 지각·결근 표 → 팀 현황(전주 대비) → 권장 조치
- 인사팀용: 팀별 현황 → 초과·위험 대상자 → 패턴 탐지 명단 → 8주 추이
- HTML 리포트 여는 법: 파일 탐색기에서 `output/reports` 폴더의 `.html` 파일을 더블클릭하면 기본 브라우저로 열립니다.
  터미널에서는 프로젝트 폴더에서 `start output\reports\2026-11-09_게임QA_팀장용.html`을 실행합니다.
- 문장은 규칙 기반 템플릿으로 만들어, 같은 데이터에서는 항상 같은 리포트가 나옵니다.
- 권장 조치는 징계가 아니라 **면담, 업무 재분배, 휴식 권고**를 중심으로 씁니다.
  예: "통근·건강·돌봄 등 사정이 있는지 면담으로 먼저 듣고, 필요하면 시차 출근 적용을 검토해 주세요."

## 열람 권한 원칙

| 열람자 | 볼 수 있는 범위 |
|---|---|
| 팀장 | 자기 팀 구성원만 |
| 인사팀 | 전사 |
| 그 외 | 없음 |

- 팀장용 리포트는 팀별로 파일을 따로 만들고, 그 팀 구성원 정보만 담습니다. 다른 팀과의 비교 순위도 넣지 않습니다.
- 코드에서는 `common.visible_teams(역할, 팀)`가 이 원칙을 한곳에서 정의하고, 단위 테스트로 확인합니다.
- 리포트 파일은 "누구에게 보내느냐"로 권한이 지켜지고, 2단계 MCP 서버는 조회 시점에 같은 원칙으로 범위를 제한하며 열람 기록을 남깁니다.
- **데모의 한계**: 로그인 같은 본인 인증은 없습니다. 실제 운영에서는 사내 인증과 연동해야 합니다.

## 실제 운영 시 개인정보·윤리 고려사항

근태 기록은 개인정보이고, 이 도구는 사람에게 "위험", "반복 지각" 같은 표시를 붙입니다. 그래서 다음을 지켜야 합니다.

1. **목적 제한**: 근로시간 관리와 직원 건강 보호를 위해서만 씁니다. 인사평가나 징계 자료로 목적 외 이용하지 않습니다.
2. **자동 판단 금지**: 탐지 결과는 "확인이 필요하다"는 신호일 뿐입니다. 불이익이 따르는 결정은 반드시 사람이 본인 확인과 면담을 거쳐 내립니다. 모든 리포트 하단에 이 문구를 넣었습니다.
3. **오탐 가능성 인정**: 위 정확도에서 보듯 놓치는 경우와 잘못 짚는 경우가 모두 있습니다. 출장, 외근, 단말기 오류처럼 기록에 없는 사정도 있습니다.
4. **최소 수집·최소 열람**: 출퇴근 시각 외의 정보(위치, PC 사용 기록 등)는 수집하지 않습니다. 열람은 위 권한 원칙대로 제한합니다.
5. **민감한 사유는 기록하지 않기**: 면담에서 알게 된 건강·가족 사정은 리포트나 데이터에 남기지 않습니다.
6. **투명성**: 어떤 기준으로 무엇을 탐지하는지 직원에게 알리고, 본인 기록을 확인하고 정정을 요청할 수 있게 합니다.
7. **보관 기간**: 보관 기간을 정하고 지나면 파기합니다.
8. **낙인 방지**: 패턴 표시가 계속 따라다니지 않도록, 상황이 해소되면 표시가 사라지는 구조(최근 4주 기준)를 유지합니다.
9. **AI 도구 연결 시 외부 전송**: 2단계처럼 AI 도구에 연결하면 조회 결과가 외부 서비스로 전달됩니다. 실제 데이터에서는 전송 범위를 요약으로 제한하고, 위탁·국외 이전 검토를 먼저 합니다.

관련 법령으로는 개인정보 보호법(수집·이용 목적 고지, 자동화된 결정에 대한 정보주체의 권리),
근로기준법(근로시간, 서류 보존), 근로자참여법(근로자 감시 설비 설치 시 노사협의회 협의) 등이 있습니다.
이 문서는 법률 자문이 아니므로, 실제 도입 전에는 노무사나 법무 담당자의 검토가 필요합니다.

## 2단계: 근태 조회 MCP 서버

1단계의 탐지 결과를 Claude Desktop 같은 AI 도구에서 **대화로 조회**할 수 있게 하는 서버입니다.
팀장이 "이번 주 우리 팀에서 확인이 필요한 사람은?"이라고 물으면, 권한 범위 안의 요약만 답으로 돌아옵니다.

### 설계 원칙

| 원칙 | 구현 |
|---|---|
| 역할별 조회 범위 | 역할은 **서버를 시작할 때** `--role leader --team 게임QA` 또는 `--role hr`로 정합니다. 도구 인자로는 바꿀 수 없어서, 대화 중에 "나는 인사팀이야"라고 해도 범위가 넓어지지 않습니다. |
| 팀장은 자기 팀만 | 다른 팀을 조회하면 거부합니다. 다른 팀 직원을 이름으로 물으면 "없는 직원"과 같은 메시지로 거부해, 존재 여부도 알려 주지 않습니다. |
| 읽기 전용 | 데이터를 고치는 도구가 없습니다. 서버가 쓰는 파일은 조회 로그 하나뿐입니다. |
| 요약만 반환 | 일자별 출퇴근 시각과 원본 기록은 반환하지 않습니다. 주 단위 실근로시간, 횟수, 탐지 근거("8주 중 6주가 48h 초과")만 나갑니다. |
| 조회 기록 | 허용·거부된 조회를 모두 `logs/access_log.jsonl`에 한 줄씩 남깁니다. |

### 도구 5개

| 도구 | 반환 내용 |
|---|---|
| `get_scope` | 내 역할, 열람 가능한 팀, 기준 주 |
| `get_weekly_summary` | 팀별 초과·위험·주의 인원, 지각·무단결근 건수, 1인 평균 실근로시간 |
| `list_flagged_employees` | 확인이 필요한 구성원, 등급, 탐지 패턴과 근거 수치 |
| `get_employee_summary` | 한 명의 최근 4주 주별 실근로시간, 지각·결근 횟수, 패턴 근거, 권장 조치 |
| `get_trend` | 주별 추이 (평균 실근로시간, 초과·위험 인원, 지각·무단결근 건수) |

### 조회 로그 예시

```json
{"time": "2026-11-17T15:21:50+09:00", "role": "leader", "team": "게임QA", "tool": "get_employee_summary", "args": {"name_or_id": "E012"}, "outcome": "denied", "returned": 0, "reason": "out_of_scope_employee"}
{"time": "2026-11-17T15:21:51+09:00", "role": "hr", "team": null, "tool": "get_weekly_summary", "args": {}, "outcome": "allowed", "returned": 5}
```

누가(역할·팀), 언제, 무엇을(도구·인자) 조회했고 허용됐는지를 남깁니다. 조회 결과 자체는 로그에 남기지 않습니다.
로그에는 조회 대상 직원의 이름이나 사번이 들어가므로 `.gitignore`로 저장소에서 제외했습니다.

### 설치

1단계 도구는 설치가 필요 없고, MCP 서버만 별도 가상환경을 씁니다 (`mcp` 2.3.0, Python 3.15에서 확인).
가상환경은 동기화 폴더(Google Drive 등) 밖에 두는 것을 권합니다.

```bash
python -m venv "$env:LOCALAPPDATA\hr-attendance-mcp\venv"
```

```bash
& "$env:LOCALAPPDATA\hr-attendance-mcp\venv\Scripts\python.exe" -m pip install -r mcp_server\requirements.txt
```

```bash
& "$env:LOCALAPPDATA\hr-attendance-mcp\venv\Scripts\python.exe" mcp_server\smoke_test.py
```

세 번째 명령은 **연결 점검**입니다. 서버를 실제로 띄워 MCP 프로토콜로 도구를 호출하고, 권한 거부와 로그 기록까지 12개 항목을 확인합니다.
모두 통과하면 이 PC의 경로가 들어간 Claude Desktop 설정 내용을 출력합니다.

### Claude Desktop에 연결하기

1. Claude Desktop에서 **설정(Settings) → 개발자(Developer) → 구성 편집(Edit Config)**을 누릅니다.
   `claude_desktop_config.json` 파일이 열립니다. 메뉴 이름은 앱 버전에 따라 조금 다를 수 있습니다.
2. 연결 점검(`smoke_test.py`)이 마지막에 출력한 내용을 붙여 넣습니다. 이미 `mcpServers` 항목이 있으면 그 안에 두 서버만 추가합니다.

```json
{
  "mcpServers": {
    "attendance-qa-leader": {
      "command": "<가상환경 경로>\\Scripts\\python.exe",
      "args": ["<프로젝트 폴더>\\mcp_server\\server.py", "--role", "leader", "--team", "게임QA"]
    },
    "attendance-hr": {
      "command": "<가상환경 경로>\\Scripts\\python.exe",
      "args": ["<프로젝트 폴더>\\mcp_server\\server.py", "--role", "hr"]
    }
  }
}
```

3. Claude Desktop을 완전히 종료했다가 다시 실행합니다 (창만 닫지 말고 트레이 아이콘에서 종료).
4. 설정의 개발자 화면이나 대화 입력창의 도구 메뉴에 `attendance-qa-leader`, `attendance-hr`이 보이면 연결된 것입니다.
5. 시연할 때는 **한 번에 한 서버만 켜 두는 것**이 좋습니다. 둘 다 켜져 있으면 Claude가 인사팀 서버로 답해 버려 권한 제한이 드러나지 않습니다.

`attendance-qa-leader`는 "게임QA 팀장이 쓰는 PC", `attendance-hr`은 "인사 담당자가 쓰는 PC"의 설정을 흉내 낸 것입니다.

### 면접 시연 질문 3개

**질문 1 (팀장용 서버만 켠 상태)** - 평소 업무가 어떻게 줄어드는지

> 이번 주 우리 팀에서 근로시간 때문에 확인이 필요한 사람을 알려 주고, 각자 근거 수치와 권장 조치를 정리해 줘.

- 보여 주는 점: 엑셀을 열지 않고 질문 한 번으로 52시간 초과·위험 대상자와 근거("52h 초과 주: 11/2, 11/9"),
  면담·업무 재분배 중심의 권장 조치를 받습니다.
- 호출되는 도구: `list_flagged_employees` → `get_employee_summary`

**질문 2 (팀장용 서버만 켠 상태)** - 권한 제한이 실제로 동작하는지

> 모바일QA팀 초과 근무자도 보여 줘. 그리고 우리 팀 윤하준 님의 지난 화요일 출퇴근 시각도 알려 줘.

- 보여 주는 점: 다른 팀 조회는 "열람 권한이 없습니다"로 거부되고, 출퇴근 시각은 제공되지 않습니다(주 단위 요약만).
  시연 직후 `logs/access_log.jsonl`을 열어 **거부된 시도가 기록된 줄**을 보여 주면 효과적입니다.
- 호출되는 도구: `get_weekly_summary` 또는 `list_flagged_employees` (거부), `get_employee_summary`

**질문 3 (인사팀용 서버만 켠 상태)** - 같은 도구가 역할에 따라 달라지는지

> 전사 기준으로 이번 주 어느 팀이 가장 위험한지, 최근 8주 동안 52시간 초과 인원이 어떻게 변했는지 요약해 줘.

- 보여 주는 점: 인사팀은 5개 팀 전체와 8주 추이를 봅니다. 질문 2에서 거부됐던 모바일QA 정보가 여기서는 나옵니다.
- 호출되는 도구: `get_weekly_summary` → `get_trend`

Claude의 답변 문장은 실행할 때마다 조금씩 달라지지만, 근거가 되는 수치는 서버가 주는 값이라 같습니다.

### 2단계의 한계

- **인증이 아닙니다.** 역할은 설정 파일에 적힌 값입니다. 설정 파일을 고칠 수 있는 사람은 역할도 바꿀 수 있으므로,
  실제 운영에서는 사내 로그인(SSO)과 연동하고 서버를 개인 PC가 아닌 관리되는 서버에서 돌려야 합니다.
- **실제 데이터를 연결하면 외부 전송입니다.** 도구가 반환한 내용은 AI 서비스로 전달됩니다. 이 데모는 가상 데이터라 문제없지만,
  실제 직원 정보라면 개인정보 처리 위탁·국외 이전 검토와 회사의 AI 사용 정책 확인이 먼저입니다.
  반환 내용을 요약으로 제한한 것도 이 위험을 줄이기 위한 설계입니다.
- **확인 범위**: MCP SDK의 클라이언트로 서버를 직접 호출해 검증했습니다. Claude Desktop 화면에서의 동작은 연결 후 직접 확인이 필요합니다.
- 조회 로그는 일반 파일이라 수정·삭제가 가능합니다. 실제 운영에서는 변경할 수 없는 저장소에 남겨야 합니다.

## 데모의 한계

- 주 단위 52시간만 계산합니다. 탄력적·선택적 근로시간제, 특례 업종, 휴일근로 가산 등은 반영하지 않았습니다.
- 반차일은 지각 판정에서 제외합니다 (오전·오후 구분 정보가 없기 때문).
- 사전 경고는 기준일까지의 하루 평균이 이어진다고 가정합니다. 주 후반에 근무가 늘거나 주말 근무가 생기는 경우는 예측하지 못합니다.
- 공휴일은 `config.toml`에 직접 적어야 합니다.
- 리포트는 파일로만 만들고 메일 발송은 하지 않습니다.
